2026-10-27, Dev B. Extend the R22 process-isolation decision: database capability roles aegis_api_role and aegis_settlement_role are NOLOGIN. Deployment logins are distinct restricted principals (local Compose uses aegis_api and aegis_settle) with the matching capability membership. Service startup validates role flags and membership; a matching role name alone proves no isolation. Do not grant superuser, role/database creation, replication or row-security bypass to either application login.

Migration ownership is separate. Compose runs the migration service using MIGRATION_DATABASE_URL; neither app process receives the owner URL. The settlement entry point owns the outbox, reconciler and webhook-confirmation loops under one TaskGroup. Source and deployment procedure: backend/app/service_security.py, backend/app/settlement/worker.py, migration 0006, docker-compose.yml and render.yaml. Refer to docs/PRD_SRS.md R22/R23 for the contract.

Parent observed local Postgres 16, migration through 0006, healthy API and settlement services, API health db=true, non-root execution and absence of Treasury/audit secrets in the API. The idle settlement smoke used fake credentials and sent no PayPal requests. This local observation does not establish Render provisioning, deployed grants or hosted secret isolation; hosted evidence is still required. Final batch suite and commit provenance are recorded in docs/SESSION_LOG.md, task state only in docs/CHECKLIST.md.

Independent final review corrected PostgreSQL16 membership semantics: own capability must be usable (USAGE), but opposite capability membership must be rejected with MEMBER even when granted INHERIT FALSE and SET TRUE. Such a role can otherwise escalate through SET ROLE. Symmetric real-login regressions passed in the final609-test PostgreSQL suite.
