2026-10-26, Dev B P1-11 review. A PostgreSQL advisory lock serializes audit appenders only when every protected read can see the writer that released it. Under REPEATABLE READ an earlier transaction snapshot can hide that writer. Require READ COMMITTED before audit append. SQLAlchemy can also return an audit row already loaded into its identity map even after the SELECT is repeated; populate_existing is required for integrity verification to re-read immutable fields from the database.

The reviewed implementation MACs every immutable event field with an explicit off-database key and verifies the prefix before append. Signed chain appends use one global advisory lock; enqueue_event only flushes an unsigned queue row and does not take that lock. It checks a caller-supplied trusted head to detect truncation and rejects malformed Unicode head input. The independent focused suite passed 30/30 against PostgreSQL 16 after the snapshot/stale-map fixes; the implementer reported full backend 464/464 on Linux Python 3.12/Postgres 16 at 46a2ecc. These are local test results, not proof of production key isolation or externally anchored history. The queue-lock description was corrected on 2026-10-27 against the reviewed source; no behavior changed.

The prefix check is O(n). Queue consumption, grants, runtime key wiring and external anchors remain separate P2-26/deployment work. Review code and tests in the audit PR; task state belongs only in docs/CHECKLIST.md. PRD R21/R22 and the linked shared security decision provide the contract.
